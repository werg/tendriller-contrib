# Native membership cost evidence — 2026-11-16

Two real native runs measured administrator traffic and storage before and after
batching one certified ledger page into one atomic durable update. The change
reduced logical administrator bytes written by **73.85% in this workload** while
retaining exactly the same 35,812 value bytes. This is a measured implementation
improvement; it is not a Cloudflare price or hosted/peer savings result.

## What the measurement changed

The former policy rewrote its complete retained evidence snapshot for every
incoming entry and every repeated certificate. The administrator receives an
already bounded page. It now validates that page and its certificate, evaluates
the prefix, then commits the page once. Validated exact duplicates perform no
durable write. A failed late entry, conflicting certificate, quota or storage
failure leaves the prior durable and in-memory prefix intact.

| Measured quantity | Baseline | Batched |
| --- | ---: | ---: |
| Administrator durable put calls, complete run | 104 | 65 |
| Administrator value bytes written, complete run | 502,606 | 131,441 |
| Ledger-category durable put calls | 49 | 10 |
| Ledger-category value bytes written | 472,219 | 101,054 |
| Retained administrator value bytes | 35,812 | 35,812 |
| Empty warm sync put calls | 1 | 0 |
| Empty warm sync value bytes written | 10,202 | 0 |

These totals include bootstrap and lifecycle work. The policy still retains the
full descriptor/certificate history and writes a full snapshot when a page
changes it. Batching and duplicate suppression do not create constant-cost
history, compaction, incremental on-disk paging or a backup. Key distribution
still depends on recipient count.

Four additional history-policy cases plus the existing membership, storage-bound
and actual native-handler checks passed: **24 tests across four files**. They
exercise the maximum 128-entry page plus certificate, exact duplicate signature
validation without writes, invalid late-item atomic refusal, conflicting signed
prefix refusal, failed storage followed by exact recovery, retained large-history
decoding and actual lost-reply/enrollment/revocation behavior.

## Payload size and candidate count are separate costs

| Actual workload | Detached envelope bytes | Encoded candidate descriptor bytes | Administrator retained-value increase |
| --- | ---: | ---: | ---: |
| 4 candidates, 16-byte body each | 2,628 | 568 | 1,973 |
| 4 candidates, 192-KiB body each | 789,052 | 576 | 1,981 |
| 8 candidates, 16-byte body each | 5,240 | 1,136 | 3,566 |

The retained-value increases include the certified membership-history update at
that stage, not only the candidate descriptors. This new native workload uses
different operation/namespace lengths from the earlier browser fixture; its
envelope totals therefore differ slightly. Each report's actual bytes remain
unchanged.

The complete batched run made 31 signed membership requests: 17,885 request-body
bytes and 29,761 response-body bytes. It transferred 34 descriptors, totaling
2,706 candidate-descriptor bytes and 10,359 inline-control descriptor bytes.
The latter already contain 8,167 inline-envelope bytes. Administrator application
envelope bytes and unexpected endpoint attempts were both **zero**. No full-peer
payload session was opened in this measurement; its peer byte counters are zero
because that route was unused here, not because P2P payload transfer is free.

The administrator closed at a 77,824-byte SQLite file while retaining 35,812
logical value bytes. The native role closed at 11,696,235 file bytes across its
projection, control store and agent store. Its agent store separately retained
802,899 detached-payload value bytes, 834,087 feed/evidence value bytes and
2,397,002 operation-journal value bytes. Copies and database overhead are real
storage costs. These snapshots are not provider GB-month billing, independent
backups, or universal database size limits.

CPU, sampled RSS and phase duration are preserved in both raw reports. Other
processes shared this machine, and both roles share the measured process. The
run makes no latency or per-role CPU guarantee and does not infer savings from
the difference between the two materializer file sizes.
